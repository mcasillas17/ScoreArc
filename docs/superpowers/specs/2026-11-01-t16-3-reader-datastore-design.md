# T16.3 reader DataStore design

Implementation authorization: the November 1 task requests implementation and an active PR. This document records engineering choices under that scope; production rollout is separately gated. Baseline `588c1ba`. Migration 0028 and resource metadata were deployed October 31 per the owner; no migration is required here.

## Approach and identity

Keep `createDataStore` as the independently callable ESPN implementation. Add `createReaderDataStore`, strict wire decoders, bounded transport, and a composition layer. Preserve all twelve method signatures, public URL formats and default API envelopes. `SCOREARC_DATA_SOURCE=reader` opts the whole joined group (all eleven non-news methods) into reader mode. Unset or `espn` selects the existing instance directly and constructs no reader client. Unknown flag values fail configuration rather than enable traffic. One group intentionally includes standings, squads and leaders: their joins and player-slug indexes cross the originally listed match group. `getNews` always delegates to ESPN; T16.6 is unresolved and the reader news route is itself a proxy.

Considered emitting canonical match UUIDs with serialized provider references. That requires changes to every match-carrying UI type/request and rollback route. Chosen instead: validate persisted mappings, then normalize reader output to the existing provider reference representation at the seam. Public team links still use `canonicalTeamId`/`providerTeamId`; player slugs still use the existing collision algorithm. No name, score, kickoff or asset-derived mapping. Nullable canonical `playerId` fields on reader leaders/lineups remain qualified data fields; they are preserved, never used as frontend lookup addresses or slugs. The normalized event id remains safe in a later request on a cold instance, with reader off, or when the detail operation falls back. Reader UUID routes only receive canonical UUIDs resolved from stored references; ESPN only receives provider references.

Existing reader HTTP surfaces do not expose complete match/player crosswalks. Add one read-only, scoped `/v1/competitions/{comp}/{season}/identities?kind=match|player|team&from=canonical|espn&ids=<comma-separated>` endpoint. Maximum 100 unique ids; exact parameter validation; fixed kind branches and parameterized SQL. Return one row per input: `{id,status,canonicalId,providerId,competitionId,seasonId,homeId,awayId}`. Status is `resolved|missing|ambiguous`; unresolved values are null. Match scope and canonical sides are required for resolved match rows; other kinds have null scope/sides. Matches outside the route scope are missing. Player/team identity is global (a valid identity can lack this season's stats). Resolve only unique bidirectional ESPN references; multiple aliases are ambiguous rather than arbitrarily selected. Existing SELECT grants/indexes suffice. Metadata contains the identity resource with honest unknown observation. No broad search and no database access from Next.js.

Use the curated team crosswalk first. Query persisted refs for provisional/unmapped teams. Missing/ambiguous optional career-team references become null associations while preserving names/seasons and the useful profile. Required player and game-log identities still fail closed. Null nested refs remain null; provisional teams still have no curated public link. Missing/ambiguous mappings needed to normalize a returned collection reject the entire reader result. An unresolved directly addressed player/match is a typed identity failure, not proof of not-found and not permission for a blind entity resurrection. An established reader profile 404 returns null, as does a confirmed ESPN profile 404 during fallback; dependency outages remain unavailable. Invalid query/side/scope is terminal, never hidden by fallback.

## Method and resource policy matrix

Every body is decoded from unknown, including all nested optional values. Every named component below must exist and have valid structure/scope, even optional components. Required collection evidence must be complete/empty and fresh/empty/dormant; dormant never overrides incomplete availability. Unknown-clock identity/detail/gameLog evidence is deliberately accepted only with structurally valid data. Optional data keeps its metadata limitations; no zero/false/empty-id fabrication.

|---|---|---|---|---|
| getMatches | matches?range=explicit-or-currentWeek&detail=summary | matches + identity | detail | all match/side/event ids; revalidate each operation |
| getFixtures | matches?range=explicit | matches + identity | none; no detail request | all match/side ids; revalidate each operation |
| getLiveWindow | matches?range=nowWindow | matches + identity | none | same; revalidate each operation |
| getUpcoming | matches?range=forwardRange&state=scheduled&limit=n | matches + identity | none | same; revalidate each operation |

Team optional schedule/squad failures retain identity with availability; malformed present data is a failure. For player identity, unknown freshness is expected; retained career and held log are useful but do not assert completeness. An optional `liveMatch` context on live player-log rows carries held state/status/minute/scores from the same reader query so popups never turn a live row into FT; finished wire vectors and default ESPN score handling remain unchanged. Reader rows without result or live context stay unlinked. Nullable starter and career team id widen the frontend contract; unknown starter is not labeled a substitute. Add optional reader evidence on composite output where needed; retain derived complete/partial/unavailable as explicit evidence without changing array envelopes. Missing inputs to derivation throw an unavailable error eligible for fallback, never return a successful empty table. Separate input HTTP reads are separate snapshots. `readerDerivation.inputs` retains their individual competition/season/resource envelopes, without a combined observation clock.

## Grouped operations and ownership

`sourceSelection.ts` owns selection and `runDataOperation(store, callback, signal?)`. A reader operation invokes a source-bound raw store; any required failure discards its entire result and reruns the callback once with an ESPN store. Nested helpers on a bound store do not create another fallback. Required collection catches recognize both controlled attempts and propagate exhausted failures; the default ESPN instance is never marked, so its existing best-effort behavior remains unchanged. Wrap standings+windows (form), standings+squads (player index), slug resolution+profile, summary+slug enrichment, leader+slug enrichment and banner current/upcoming reads, plus homepage sports feeds, merged team directories, and required standings/cup page data groups. Reader summary enrichment is awaited under the shared reader deadline so a pending or failed index cannot bypass grouped fallback; ESPN retains its existing 800ms optional-link timeout. No process-global health switch and no negative availability cache. Match and team ids use one stable frontend representation even between independently timed responses. Window rows retain their validated resource evidence, including optional retained-detail limitations.

`readerTransport.ts` owns server-configured origin, fixed paths, encoded query, redirect rejection, bytes and deadlines. `readerDecode.ts` owns runtime DTO validation. `apiStore.ts` owns per-method resource/body/identity semantics and source-only caching. `sourceSelection.ts` owns the total deadline and single fallback. `standingsForm.ts` scopes in-flight sharing by store identity. Existing indexes depend on DataStore only, never reader modules; type-only imports prevent adapter cycles.

## Freshness, transport and cost

Reader origin is server-only `SCOREARC_READER_ORIGIN`, HTTPS in production. Loopback is allowed only outside production (including HTTPS loopback); other origins require HTTPS. Reject credentials, fragments, query, path prefixes, unsupported schemes and unsafe redirects. No NEXT_PUBLIC setting, probes, shadows, scheduler or retries. A caller abort cancels outstanding work and cannot start fallback. Internal reader timeout may fall back. 429, network, 5xx, malformed metadata/body and required stale/unavailable evidence may fall back once; 400, other unexpected 4xx, identity ambiguity on an addressed entity and semantic scope/side mismatch are terminal. If both sources fail, propagate the existing route unavailable path.

Total operation deadline 25s, reader attempt 5s, fallback uses the remaining deadline. Per response 4 MiB, combined operation 32 MiB, at most 128 transport calls, at most four in flight. Queue wait and streaming body time count. Crosswalk batches are at most 100 and bounded by the same operation. Reject over-budget operations rather than truncate. ESPN fallback transport shares those total budgets when reader mode is enabled; disabled mode preserves its existing behavior.

Reader and ESPN caches are separate. Reader keys include origin, scope, route/query and provider-normalization policy. Store only successful reader bytes/evidence, never fallback results. Revalidate resource evidence on cache reuse, including observation expiry at 20m standings/leaders, 25h squad/stats, 32d career; do not cache core match/bracket/summary/team reads because their aggregate observation clocks cannot establish a safe remaining lifetime. Identity mappings are revalidated per operation, no persistent mapping cache is necessary for correctness. Caller cancellation must be checked before using a cache hit.

Expected cold calls before identity batches: windows/bracket/team/squad 1, summary/player 2 including address resolution, leaders 2, MLS standings 1, Leagues Cup 3. Warm reader body cache avoids data reads; identity verification remains bounded and measured. Player index uses one squad per distinct team, no profile fan-out. Enriched windows cost one body read, no summary fan-out. Fallback reruns a complete operation once. Telemetry uses bounded method/reason enums and throttling, without ids, URLs, bodies or raw errors.

## Builder-check rulings

- A derived `partial` result with zero groups has nowhere to carry per-group issues in the unchanged array envelope. Treat it as a typed unavailable reader result and rerun the whole operation on ESPN; never serialize that result as an unexplained successful `[]`. Complete empty results remain valid and never fall back for emptiness.
- Validate source/derivation as well as scope for every expected metadata component, including optional components. Current identity is mixed/mixed; detail is espn/retained; matches, standings, leaders, seasonStats and career are espn/direct; squad is espn/current-roster; bracket, gameLog and participation are espn/derived. The parser's enum validation alone does not establish these route semantics.
- A summary 404 can mean a known match has no retained detail. The identity resolver establishes that match separately; this is distinct from an established profile not-found and must not be described as proof that the match does not exist.

## Review repairs and measured calls

The adapter preserves distinct standings tables sharing a display-derived group id; uniqueness is required only for teams inside each table. Reader game-log stat headings and accessible titles cover all 15 fields in EN/ES.

Local HTTP self-check: Leagues Cup standings cost 4 cold / 2 warm reader calls; the full adapter exercise cost 33 calls and 307,060 response bytes. Isolated transport tests measure failed summary fallback at 3 cold upstream calls (identity, reader summary, ESPN summary) and 2 warm calls (identity, reader summary; only ESPN owns its cached summary). T7.3 contract navigation costs 4 table / 6 form / 2 popup reader calls on separate cold instances. These are bounded fixture measurements, not production parity or latency acceptance.

Current-scope transport measurements for complete joined consumers: homepage sports reads 36 cold / 18 warm calls; merged team directory 13 cold / 2 warm; each below 1 MiB with peak concurrency four. No budget was raised to accommodate these joins.
